# راهنمای استقرار و رفع گیر کردن صفحه بارگذاری

## نشانه‌ای که گزارش شد

پس از استقرار، صفحه روی پیام «در حال آماده‌سازی فضای کاری شما...» می‌ماند و هیچ خطا یا دکمه «تلاش دوباره» دیده نمی‌شد.

## علت اصلی

کل بارگذاری فضای کار به یک درخواست وابسته است:

1. `src/app/page.tsx` کامپوننت کلاینت `Workspace` را رندر می‌کند؛ تا وقتی `data` خالی است، صفحه بارگذاری نشان داده می‌شود (خط ۵۳۰ `src/components/workspace.tsx`).
2. `Workspace` در نخستین اجرا `/api/workspace` را صدا می‌زند.
3. `/api/workspace` به پایگاه داده وصل می‌شود (`currentUser` → ساخت کاربر مهمان → چند پرس‌وجو).

دو نقطه در همین زنجیره «بی‌نهایت» بود:

- استخر اتصال `pg` در `src/db/index.ts` هیچ مهلتی نداشت؛ مقدار پیش‌فرض `connectionTimeoutMillis` صفر است، یعنی اگر میزبان پایگاه داده در دسترس نباشد یا SYN را رها کند، درخواست هرگز تمام نمی‌شود.
- `fetch` در `src/components/workspace.tsx` هم مهلت (timeout) و abort نداشت، پس وعده‌ای که هرگز حل نمی‌شد، اسپینر را برای همیشه نگه می‌داشت.

نتیجه: اگر `DATABASE_URL` روی سرور تنظیم نشده باشد، به میزبان اشتباه/مسدود اشاره کند، یا جدول‌ها ساخته نشده باشند، کاربر فقط اسپینر می‌بیند. (جدول‌ها در این پروژه با `drizzle-kit push` و به‌صورت دستی ساخته می‌شدند و هیچ مهاجرتی همراه برنامه نبود؛ بنابراین پایگاه داده تازه‌ی استقرار خالی است.)

نکته مهم: با یک پایگاه داده سالم، همان مسیر در محیط تولید محلی در حدود ۱۰۰ میلی‌ثانیه پاسخ می‌دهد؛ بنابراین کندی ذاتی کد نیست.

## چه چیزی اصلاح شد

| فایل | تغییر |
| --- | --- |
| `src/db/index.ts` | مهلت اتصال (۸ ثانیه)، `statement_timeout` و `query_timeout` (۱۵ ثانیه)، نگه‌داشتن اتصال (`keepAlive`) و عدم کرش هنگام نبودن `DATABASE_URL` |
| `src/db/errors.ts` | تبدیل خطاهای پایگاه داده به پیام فارسی و راهنمای رفع (اتصال، احراز هویت، نبود جدول، SSL…) |
| `src/lib/api.ts` | `apiFailure` خطاهای پایگاه داده را با کد ۵۰۳ و پیام قابل‌فهم برمی‌گرداند |
| `src/db/migrate.ts` + `src/db/schema-sql.ts` | ساخت خودکار و idempotent جدول‌ها در نخستین درخواست (با قفل advisory) |
| `drizzle/0000_init.sql` | مهاجرت رسمی Drizzle، هم‌تراز با `src/db/schema.ts` |
| `src/app/api/health/route.ts` | گزارش دقیق: پیکربندی، دسترسی و آماده بودن شِما |
| `src/components/workspace.tsx` | مهلت ۲۰ ثانیه برای درخواست، یک تلاش دوباره خودکار، پیام خطا و دکمه «تلاش دوباره»، هشدار کندی پس از ۹ ثانیه |
| `src/proxy.ts` | `upgrade-insecure-requests` فقط روی درخواست HTTPS (روی استقرار HTTP باعث می‌شد دارایی‌ها هرگز بارگذاری نشوند) |
| `src/lib/auth.ts` | کوکی نشست روی استقرار HTTP امن‌سازی نمی‌شود تا هر درخواست مهمان تازه نسازد |

## چک‌لیست استقرار

1. متغیر `DATABASE_URL` را روی سرویس استقرار تنظیم کنید (مثلاً `postgresql://user:pass@host:5432/db?sslmode=require`).
2. برنامه را راه‌اندازی کنید؛ شِما در نخستین درخواست خودکار ساخته می‌شود. برای ساخت پیش از باز شدن سایت: `npm run db:push`.
3. نشانی `/api/health` را باز کنید؛ پاسخ موفق:

```json
{ "ok": true, "database": { "configured": true, "reachable": true, "schemaReady": true, "latencyMs": 12 } }
```

4. سپس صفحه اصلی باید فضای کار را نشان دهد.

## متغیرهای محیطی اختیاری

| متغیر | پیش‌فرض | کاربرد |
| --- | --- | --- |
| `DATABASE_URL` | — | اتصال پایگاه داده (الزامی) |
| `DB_CONNECT_TIMEOUT_MS` | `8000` | مهلت برقراری اتصال |
| `DB_STATEMENT_TIMEOUT_MS` | `15000` | مهلت هر پرس‌وجو |
| `DB_POOL_MAX` | `10` | بیشینه اتصال همزمان |
| `AUTO_MIGRATE` | `true` | ساخت خودکار شِما؛ با `false` غیرفعال می‌شود |

## عیب‌یابی

```bash
# همان اتصالی که برنامه استفاده می‌کند، با مهلت واقعی
DATABASE_URL="postgresql://…" npm run db:check

# وضعیت سرور مستقر
curl -s https://your-domain/api/health
```

خطاهای رایج و پیام‌های متناظر در رابط کاربری:

| کد | معنا | راه‌حل |
| --- | --- | --- |
| `DATABASE_URL_MISSING` | متغیر تنظیم نشده | تنظیم متغیر محیطی و راه‌اندازی مجدد |
| `CONNECT_FAILED` | اتصال برقرار نشد یا بیش از ۸ ثانیه طول کشید | دسترسی شبکه، صحت میزبان/پورت، فعال بودن پایگاه داده |
| `28P01` / `28000` | نام کاربری یا رمز نامعتبر | تصحیح `DATABASE_URL` |
| `3D000` | پایگاه داده وجود ندارد | ساخت دیتابیس |
| `42P01` | جدول‌ها ساخته نشده‌اند | `npm run db:push` یا راه‌اندازی مجدد با `AUTO_MIGRATE=true` |
| `SSL` | اتصال امن برقرار نشد | افزودن `?sslmode=require` |

## نکته‌های میزبان

- اگر میزبان فقط IPv6 یا فقط IPv4 مسیر می‌دهد، از میزبان اتصال‌دهنده (pooler) سرویس پایگاه داده استفاده کنید؛ خطای `ENOTFOUND`/مهلت اتصال معمولاً همین است.
- سرویس‌های serverless با پایگاه داده‌ی در حالت خواب (scale-to-zero) ممکن است نخستین درخواست را کند کنند؛ مهلت ۸ ثانیه برای بیدار شدن کافی است و در غیر این صورت پیام خطا نمایش داده می‌شود، نه اسپینر بی‌پایان.
- روی استقرار HTTP (بدون TLS) هدر `upgrade-insecure-requests` و کوکی `Secure` می‌توانند کل برنامه را از کار بیندازند؛ هر دو در این نسخه بر اساس پروتکل واقعی درخواست تنظیم می‌شوند.
